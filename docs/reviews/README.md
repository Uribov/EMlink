# docs/reviews —— 审查与修复留档

本目录保存 EMlink 的**审查 → 修复**全过程，供后续（人或子 agent）追溯"哪一条为什么这么改、怎么验证的、还剩什么没做"。

## 目录内容

| 文件/目录 | 内容 |
|---|---|
| `CODE_REVIEW_2026-10-14.md` | 交付级代码审查日志（审查时的原始记录，**不修改**，作为历史基线） |
| `FIX_LOG.md` | 修复对照表：条目 → 提交 → 改了什么 → 怎么验证的 → 遗留项 |
| `briefs/` | 每个修复项的**任务书**（交给 OpenCode 的精确改动规格 + 自检题） |

`briefs/` 命名：`P0-N_brief.md`（上板前阻断项）、`AN_brief.md`（M1 交付级）。同一项若拆成几步，用 `A5a/A5b/A5c` 后缀。

## 固定工作流（每个修复项都一样）

1. **写任务书**（`briefs/AN_brief.md`）：背景 + 允许改动的文件白名单 + 逐条精确改法（到行/函数/新代码）+ 自检问题 + 验收要求
2. **AI 生成代码**：OpenCode（DeepSeek 官网通道）按任务书改，硬性禁止：改 `.md`、跑编译、`git commit`
3. **逐行审 diff**：确认与任务书一致、没有越界改动、逻辑（尤其并发/位运算/边界）手算验证
4. **编译 + 独立验证**：`pio run`；能脱离硬件的部分做真验证（例：`airtime_ms()` 抽到主机侧编译跑断言，比对 Semtech 表格）
5. **同步文档 + 分项提交**：改哪个模块就更新该模块的 `.md`（含实现架构一节）+ 总架构相关章节，然后**单独一个提交**

> 代码与文档**必须同一个提交**：`firmware/src/<模块>.md` 的约定是"前半约束、后半实现架构"，改代码不更新它会让后续子 agent 读到过期规格。

## 通道说明

- 主力：**DeepSeek 官网 API**（`~/.local/bin/oc-deepseek`，透传 `-f 任务书`）
- 南航 token 服务：**限流严重且会被校园网 WAF 拦**，非手动指定不使用
