# docs/reviews —— 审查与修复留档

本目录保存 EMlink 的**审查 → 修复**全过程，供后续（人或子 agent）追溯"哪一条为什么这么改、怎么验证的、还剩什么没做"。

## 目录内容

| 文件/目录 | 内容 |
|---|---|
| `CODE_REVIEW_2026-10-14.md` | 交付级代码审查日志（审查时的原始记录，**不修改**，作为历史基线；条目现状见 `FIX_LOG.md`） |
| `STATIC_AUDIT_2026-10-15.md` | 静态排查（"上板才炸"的 8 类模式）：6 处真问题 + 4 类干净负结果；**不主动修**，改为现象驱动 |
| `FIX_LOG.md` | ⭐ **权威记录**：条目 → 提交 → 改了什么 → 怎么验证的 → 遗留项。想知道"现在到哪一步"看这个 |
| `briefs/` | 进行中的任务书；**已完成的归档在 `briefs/archive/`**（规矩与模板见 `briefs/README.md`） |

## 固定工作流（每个修复项都一样）

1. **写任务书**（`briefs/<ID>_brief.md`）：背景（贴原代码 + 说清后果）+ 允许改动的文件白名单 + 逐条精确改法（到行/函数/新代码）+ 自检问题 + 报告要求（含"诚实列出不能保证什么"）
2. **AI 生成代码**：OpenCode（DeepSeek 官网通道）按任务书改，硬性禁止：改 `.md`、跑编译、`git commit`、读仓库外路径
3. **逐行审 diff**：确认与任务书一致、没有越界改动、逻辑（尤其并发/位运算/边界）手算验证；可用脚本筛"非注释改动"来验证纯注释类任务
4. **编译 + 独立验证**：`pio run`；能脱离硬件的部分做真验证（例：`airtime_ms()` 抽到主机侧编译跑断言，比对 Semtech 表格）
5. **同步文档 + 分项提交**：改哪个模块就更新该模块的 `.md`（含实现架构一节）+ 总架构相关章节，然后**单独一个提交**

> 代码与文档**必须同一个提交**：`firmware/src/<模块>.md` 的约定是"前半约束、后半实现架构"，改代码不更新它会让后续子 agent 读到过期规格。

## 两条硬规矩（都是踩过坑换来的）

- **技术事实必须查官方文档 + 留档**：芯片/模块/协议参数（合法参数组合、驱动匹配规则、寄存器默认值…）**不许凭记忆或口述断言**。
  查完把"结论 + 原始出处"写进 `../references/`（例：`../references/LLCC68_E220-900M22S.md` —— 一次凭记忆说"LLCC68 不支持 CAD"，实际手册 §6.1.5 明确支持）。
- **报告必须附"人话版"**：任何审查/方案/结论，前面先给一段不用术语、面向嵌入式新手的摘要。

## 通道说明

- 主力：**DeepSeek 官网 API**（`~/.local/bin/oc-deepseek`，透传 `-f 任务书`）
- 南航 token 服务：**限流严重且会被校园网 WAF 拦**，非手动指定不使用
