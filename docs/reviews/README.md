# docs/reviews —— 审查与修复留档

本目录保存 EMlink 的**审查 → 修复**结果，供后续（人或子 agent）追溯"哪一条为什么这么改、怎么验证的、还剩什么没做"。

> **只留结论，不留过程稿。** 任务书（施工单）写的是一次性的"打算怎么改"，改完就过期，留着会变成幻觉来源 ——
> **用户 2026-10-17 明确：任务书不进仓库**，只放本地 `~/EMlink-briefs/` 作为参考（规矩见 `briefs/README.md`）。

## 目录内容

| 文件/目录 | 内容 |
|---|---|
| `FIX_LOG.md` | ⭐ **权威记录**：条目 → 提交 → 改了什么 → 怎么验证的 → 遗留项。想知道"现在到哪一步"看这个 |
| `STATIC_AUDIT_2026-10-15.md` | 静态排查（"上板才炸"的 8 类模式）：6 处真问题 + 4 类干净负结果。**这是候选清单、不是待办** —— 处理由真实现象驱动 |
| `CODE_REVIEW_2026-10-14.md` | 第一轮交付级审查日志（**历史基线，不修改**）。⚠️ 里面描写的多为"当时的问题"，**多数已修** —— 现状一律以 `FIX_LOG.md` 为准，别照着它去"重新修一遍" |
| `briefs/` | 任务书的**规矩与模板**。任务书本体**不进仓库**：源文件在 `~/EMlink-briefs/`，调用 OpenCode 时临时复制为 `briefs/_active.md`（已被 `.gitignore` 忽略），跑完即删 |

> **状态图例**（本目录、`docs/plans/`、`ROADMAP.md`、`todo.md` 通用）：
> ✅ 已实施　🔶 部分完成　⬜ 未做（已排队）　⏸ 推后（写明触发条件）　🕐 只能上板确认
> 每份"问题/方案"类文档顶部都应有这张状态块 —— 否则读者会把**过期意图**当成**当前事实**（这是本项目明确要避免的幻觉来源）。

## 固定工作流（每个修复项都一样）

1. **写任务书**（`~/EMlink-briefs/<ID>_brief.md`，仓库外）：背景（贴原代码 + 说清后果）+ 允许改动的文件白名单 + 逐条精确改法（到行/函数/新代码原文）+ 自检问题 + 报告要求（含"诚实列出不能保证什么"）
2. **AI 生成代码**：OpenCode（DeepSeek 官网通道）按任务书改，硬性禁止：改 `.md`、跑编译、`git commit`、读仓库外路径
3. **逐行审 diff**：确认与任务书一致、没有越界改动、逻辑（尤其并发/位运算/边界）手算验证；纯注释类任务可用脚本筛"非注释改动"来验证
4. **编译 + 独立验证**：`pio run`；能脱离硬件的部分做真验证（例：`airtime_ms()` 抽到主机侧编译跑断言，比对 Semtech 表格）
5. **同步文档 + 分项提交**：改哪个模块就更新该模块的 `.md`（含实现架构一节）+ 总架构相关章节；然后**单独一个提交**。任务书本来就不在仓库里，无需删除

> 代码与文档**必须同一个提交**：`firmware/src/<模块>.md` 的约定是"前半约束、后半实现架构"，改代码不更新它会让后续子 agent 读到过期规格。

## 两条硬规矩（都是踩过坑换来的）

- **技术事实必须查官方文档 + 留档**：芯片/模块/协议参数（合法参数组合、驱动匹配规则、寄存器默认值…）**不许凭记忆或口述断言**。
  查完把"结论 + 原始出处"写进 `../references/`（例：`../references/LLCC68_E220-900M22S.md` —— 一次凭记忆说"LLCC68 不支持 CAD"，实际手册 §6.1.5 明确支持）。
- **报告必须附"人话版"**：任何审查/方案/结论，前面先给一段不用术语、面向嵌入式新手的摘要。

## 通道说明

- 编程子 agent：**OpenCode + DeepSeek 官网 API**（`~/.local/bin/oc-deepseek`，透传 `-f 任务书`）—— 唯一在用的通道
