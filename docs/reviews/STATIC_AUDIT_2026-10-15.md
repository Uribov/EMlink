> **性质**：**只读排查**，未改动任何代码。
> **动机**：第一轮产品级审查（`CODE_REVIEW_2026-10-14.md`）看的是**逻辑与契约**；这一轮专扫**第一轮看不到、只有上板才会炸**的维度 —— 时序 / 时间回绕 / 中断 / 并发 / 栈 / 边界 / 内存。

## 0. 人话版摘要（给非嵌入式读者）

1. 这轮专门找"上电才发作"的毛病，一共扫了 8 类：节拍、时间、中断、并发、栈、边界、内存。
2. **没有"一上电就炸"的硬伤**，但有 6 处"特定条件下才出问题"的真毛病（下面第 3 节）。
3. 最要紧的一条：**分片重组那套"定时清理"在链路一忙时就永远不会跑**（因为它只在"100 毫秒没收到包"时才被调用）。链路越忙越不跑，恰好是大包最容易碎的时候。
4. 第二条：**在最大扩频因子（SF11）下发最大包并重传时，喂狗窗口逼近 5 秒红线**——看门狗会把板子重启。SF≤10 没事。
5. 第三条：WiFi 维护网页那个对象，**"关了马上再开"可能删错对象导致崩溃**（正常慢慢操作碰不到）。
6. 还有三条较轻的：切速率的节拍会被大包发送拖延、降频统计表两个核同时改（只影响统计数字）、开机次数计数器 8 位会回绕（同密钥开机 256 次后加密安全性略降，已在"已知限制"里）。
7. 反过来说，**好几类彻底干净**：时间比较没有回绕坑、加了锁的地方没有"忘记解锁"、网络来的数字当下标都有范围检查、也没有裸的内存申请。
8. 有 4 件事只能在板子上量（栈还剩多少、SF11 会不会重启、中断会不会漏、射频库内部栈多深）——已进 `todo.md`。
9. 难查程度：第 3 条要连续大流量才复现（中等）；第 4 条要示波器/串口日志（难）；其余都容易定位。
10. 建议：第 3、4、5 条现在就能用小改动修掉（每个 1~5 行、都是"加保护"性质）；切速率那条等上板看真实现象再定方案。

## 4. 助手核实的"仓库外问题"（库在仓库内，可查）

- **RadioLib `transmit()` 的阻塞上限**（`firmware/lib/radiolib/src/modules/SX126x/SX126x.cpp:241-242`）：
  `timeout = (getTimeOnAir(len) * 5) / 1000;` → **超时 = 发射空中时间的 5 倍**。
  含义：正常发射 ≈ 1×ToA（SF11/200B ≈ 3.9s，**不喂狗但 < 5s ✔**）；若 TX 完成中断丢失，最多等到 5×ToA（≈20s）→ 但此时 **WDT 会先在 5s 把整机复位** ✔ 属设计兜底，不是静默死锁。
- **库内调用深度**（`readData` / `Adafruit_NeoPixel::show()`）：数值可在库内查，但**价值低** —— 上板用栈高水线量一次更直接（见 §6）。

## 5. 有价值的负结果（已排查、未发现问题）

1. **时间回绕安全**：全仓 25 处时间比较逐条分类，全部走"无符号差值"或"先后顺序用有符号差值"；唯一"绝对时间"判断（`ota.cpp:338` 的 `millis() < 10000`）有一次性开关保护 → **无回绕坑**。
2. **临界区闭合**：`route / addr_map / crypto / mesh` 约 40 处 `portENTER_CRITICAL`，**每条 return 分支都成对** → 未发现"上锁忘解锁"。
3. **网络来的下标**：`mav_router`（payload 偏移）、`frame_codec`（长度）、`frag`（片序号/长度）、`cli`（邻居循环）**全部有范围检查**。
4. **无裸动态分配**：grep 命中的 `malloc/calloc/free` 2 处是 mbedTLS 上下文反初始化（栈对象）与注释里的字样。
